<a id="getting-started"></a>
# Начало работы

Добро пожаловать в Caddy! В этом руководстве рассматриваются основы использования Caddy, чтобы вы на общем уровне освоились с ним.

**Цели:**
- 🔲 Запустить daemon
- 🔲 Попробовать API
- 🔲 Передать Caddy конфигурацию
- 🔲 Проверить конфигурацию
- 🔲 Создать Caddyfile
- 🔲 Использовать адаптер конфигурации
- 🔲 Запустить с начальной конфигурацией
- 🔲 Сравнить JSON и Caddyfile
- 🔲 Сравнить API и конфигурационные файлы
- 🔲 Запустить в фоне
- 🔲 Перезагрузить конфигурацию без простоя

**Предварительные требования:**
- Базовые навыки работы с терминалом / командной строкой
- Базовые навыки работы с текстовым редактором
- `caddy` и `curl` в вашем PATH

---

**Если вы [установили Caddy](/docs/install) через менеджер пакетов, Caddy уже может быть запущен как сервис. В таком случае остановите сервис перед прохождением этого руководства.**

Начнем с запуска:

<pre><code class="cmd bash">caddy</code></pre>

Упс; без подкоманды команда `caddy` только выводит текст справки. Ее можно использовать каждый раз, когда вы забыли, что делать дальше.

Чтобы запустить Caddy как daemon, используйте подкоманду `run`:

<pre><code class="cmd bash">caddy run</code></pre>

<aside class="complete">Запустить daemon</aside>

Эта команда будет работать бесконечно, но что она делает? Сейчас... ничего. По умолчанию конфигурация Caddy ("config") пустая. Это можно проверить через [admin API](/docs/api) в другом терминале:

<pre><code class="cmd bash">curl localhost:2019/config/</code></pre>

<aside class="tip">

Это **не** ваш сайт: административная конечная точка на localhost:2019 используется для управления Caddy и по умолчанию доступна только с localhost.

</aside>


<aside class="complete">Попробовать API</aside>

Чтобы Caddy начал приносить пользу, ему нужно передать конфигурацию. Это можно сделать разными способами, но в следующем разделе мы начнем с POST-запроса к конечной точке [/load](/docs/api#post-load) с помощью `curl`.



<a id="your-first-config"></a>
## Ваша первая конфигурация

Чтобы подготовить запрос, нам нужно создать конфигурацию. По своей сути конфигурация Caddy — это просто [документ JSON](/docs/json/).

Сохраните это в JSON-файл (например, `caddy.json`):

```json
{
	"apps": {
		"http": {
			"servers": {
				"example": {
					"listen": [":2015"],
					"routes": [
						{
							"handle": [{
								"handler": "static_response",
								"body": "Hello, world!"
							}]
						}
					]
				}
			}
		}
	}
}
```

<aside class="tip">

Вы не обязаны использовать конфигурационные файлы, но в этом руководстве мы будем их использовать. [Admin API](/docs/api) Caddy предназначен для использования другими программами или скриптами.

</aside>


Затем загрузите его:

<pre><code class="cmd bash">curl localhost:2019/load \
	-H "Content-Type: application/json" \
	-d @caddy.json
</code></pre>

<aside class="complete">Передать Caddy конфигурацию</aside>

Можно проверить, что Caddy применил новую конфигурацию, еще одним GET-запросом:

<pre><code class="cmd bash">curl localhost:2019/config/</code></pre>

Проверьте, что она работает: откройте [localhost:2015](http://localhost:2015) в браузере или используйте `curl`:

<pre><code class="cmd"><span class="bash">curl localhost:2015</span>
Hello, world!</code></pre>

Если вы видите *Hello, world!*, поздравляем — все работает! Всегда полезно убедиться, что конфигурация работает так, как вы ожидаете, особенно перед развертыванием в production.

<aside class="complete">Проверить конфигурацию</aside>


<a id="your-first-caddyfile"></a>
## Ваш первый Caddyfile

Это было *довольно много работы* просто для Hello World.

Другой способ настроить Caddy — использовать [**Caddyfile**](/docs/caddyfile). Ту же конфигурацию, которую выше мы записали в JSON, можно выразить так:

```caddy
:2015

respond "Hello, world!"
```


Сохраните это в файл с именем `Caddyfile` (без расширения) в текущем каталоге.

<aside class="complete">Создать Caddyfile</aside>

Остановите Caddy, если он уже запущен (<kbd>Ctrl</kbd>+<kbd>C</kbd>), затем выполните:

<pre><code class="cmd bash">caddy adapt</code></pre>

Или, если вы сохранили Caddyfile в другом месте либо назвали его иначе, чем `Caddyfile`:

<pre><code class="cmd bash">caddy adapt --config /path/to/Caddyfile</code></pre>

Вы увидите JSON-вывод! Что здесь произошло?

Мы только что использовали [*адаптер конфигурации*](/docs/config-adapters), чтобы преобразовать наш Caddyfile в собственную JSON-структуру Caddy.

<aside class="complete">Использовать адаптер конфигурации</aside>

Мы могли бы взять этот вывод и сделать еще один API-запрос, но можем пропустить все эти шаги, потому что команда `caddy` сделает это за нас. Если в текущем каталоге есть файл с именем Caddyfile и другая конфигурация не указана, Caddy загрузит Caddyfile, адаптирует его за нас и сразу запустит.

Теперь, когда в текущей папке есть Caddyfile, снова выполним `caddy run`:

<pre><code class="cmd bash">caddy run</code></pre>

Или, если ваш Caddyfile находится в другом месте:

<pre><code class="cmd bash">caddy run --config /path/to/Caddyfile</code></pre>

(Если он называется иначе и имя не начинается с "Caddyfile", нужно указать `--adapter caddyfile`.)

Теперь вы можете снова загрузить свой сайт и увидите, что он работает!

<aside class="complete">Запустить с начальной конфигурацией</aside>

Как видите, есть несколько способов запустить Caddy с начальной конфигурацией:

- Файл с именем Caddyfile в текущем каталоге
- Флаг `--config` (при необходимости вместе с флагом `--adapter`)
- Флаг `--resume` (если конфигурация была загружена ранее)


<a id="json-vs-caddyfile"></a>
## JSON и Caddyfile

Теперь вы знаете, что Caddyfile просто преобразуется в JSON за вас.

Caddyfile кажется проще JSON, но всегда ли нужно использовать именно его? У каждого подхода есть плюсы и минусы. Ответ зависит от ваших требований и сценария использования.

JSON | Caddyfile
-----|----------
Легко генерировать | Легко писать вручную
Легко программировать | Неудобно автоматизировать
Чрезвычайно выразительный | Умеренно выразительный
Полный набор возможностей Caddy | Большинство возможностей Caddy
Позволяет обходить конфигурацию | Нельзя обходить внутри Caddyfile
Частичные изменения конфигурации | Только изменения всей конфигурации
Можно экспортировать | Нельзя экспортировать
Совместим со всеми API endpoints | Совместим с некоторыми API endpoints
Документация генерируется автоматически | Документация написана вручную
Повсеместный | Нишевый
Более эффективный | Более затратный по вычислениям
Немного скучный | Немного веселый
**Подробнее: [структура JSON](/docs/json/)** | **Подробнее: [документация Caddyfile](/docs/caddyfile)**

Вам нужно решить, что лучше подходит для вашего сценария.

Важно отметить, что и JSON, и Caddyfile (а также [любой другой поддерживаемый адаптер конфигурации](/docs/config-adapters)) можно использовать с [API Caddy](/docs/api). Однако полный набор возможностей Caddy и функций API доступен при использовании JSON. Если используется адаптер конфигурации, единственный способ загрузить или изменить конфигурацию через API — конечная точка [/load](/docs/api#post-load).

<a id="api-vs-config-files"></a>
## API и конфигурационные файлы

<aside class="tip">

Под капотом даже конфигурационные файлы проходят через API endpoints Caddy; команда `caddy` просто оборачивает эти API-вызовы для вас.

</aside>


Вам также нужно решить, будет ли ваш рабочий процесс основан на API или CLI. (Вы *можете* использовать и API, и конфигурационные файлы на одном сервере, но мы этого не рекомендуем: лучше иметь один источник истины.)

API | Config files
----|-------------
Вносить изменения конфигурации HTTP-запросами | Вносить изменения конфигурации shell-командами
Легко масштабировать | Сложно масштабировать
Сложно управлять вручную | Легко управлять вручную
Очень весело | Тоже весело
**Подробнее: [руководство по API](/docs/api-tutorial)** | **Подробнее: [руководство по Caddyfile](/docs/caddyfile-tutorial)**

<aside class="tip">
	Ручное управление конфигурацией сервера через API вполне возможно при наличии подходящих инструментов, например любого REST-клиента.
</aside>

Выбор рабочего процесса на API или конфигурационных файлах не зависит от использования адаптеров конфигурации: можно использовать JSON, но хранить его в файле и применять интерфейс командной строки; и наоборот, можно использовать Caddyfile через API.

Но большинство пользователей выбирают сочетания JSON+API или Caddyfile+CLI.

Как видите, Caddy хорошо подходит для множества сценариев использования и вариантов развертывания!

<a id="start-stop-run"></a>
## Start, stop, run

Поскольку Caddy — это сервер, он работает неопределенно долго. Это означает, что ваш терминал не освободится после выполнения `caddy run`, пока процесс не будет завершен (обычно с помощью <kbd>Ctrl</kbd>+<kbd>C</kbd>).

Хотя `caddy run` — самый распространенный и обычно рекомендуемый вариант (особенно при создании системного сервиса!), вместо него можно использовать `caddy start`, чтобы запустить Caddy в фоне:

<pre><code class="cmd bash">caddy start</code></pre>

После этого терминал снова будет доступен, что удобно в некоторых интерактивных headless-средах.

Затем вам придется остановить процесс самостоятельно, поскольку <kbd>Ctrl</kbd>+<kbd>C</kbd> не остановит его за вас:

<pre><code class="cmd bash">caddy stop</code></pre>

Или используйте [конечную точку /stop](/docs/api#post-stop) API.

<a id="reloading-config"></a>
## Перезагрузка конфигурации

Ваш сервер может выполнять перезагрузку/изменение конфигурации без простоя.

Все [API endpoints](/docs/api), которые загружают или изменяют конфигурацию, выполняют это плавно и без простоя.

При использовании командной строки может возникнуть соблазн нажать <kbd>Ctrl</kbd>+<kbd>C</kbd>, чтобы остановить сервер, а затем запустить его снова для применения новой конфигурации. Не делайте так: остановка и запуск сервера не связаны с изменениями конфигурации и приведут к простою.

<aside class="tip">
	Остановка сервера приведет к недоступности сервера.
</aside>

Вместо этого используйте команду [`caddy reload`](/docs/command-line#caddy-reload) для плавного изменения конфигурации:

<pre><code class="cmd bash">caddy reload</code></pre>

На самом деле под капотом она просто использует API. Она загрузит и, если нужно, адаптирует ваш конфигурационный файл в JSON, а затем плавно заменит активную конфигурацию без простоя.

Если при загрузке новой конфигурации возникнут ошибки, Caddy откатится к последней рабочей конфигурации.

<aside class="tip">
	Технически новая конфигурация запускается до остановки старой, поэтому короткое время работают обе конфигурации! Если новая конфигурация завершается ошибкой, она прерывается с ошибкой, а старая просто не останавливается.
</aside>
