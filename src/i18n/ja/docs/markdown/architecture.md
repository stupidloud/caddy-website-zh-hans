<a id="architecture"></a>
アーキテクチャ
================

Caddy は Go で書かれているため、外部依存のない、単一の自己完結した静的バイナリです。この性質は、デプロイを簡単にし、本番環境での面倒なトラブルシューティングを減らすため、プロジェクトのビジョンの重要な一部です。

動的リンクがないなら、どうやって拡張できるのでしょうか。Caddy には新しいプラグインアーキテクチャがあり、外部の（動的リンクされた）依存を持つ他のどの Web サーバーよりも、はるかに広く機能を拡張できます。

「動く部品を少なくする」という私たちの考え方は、最終的に、より信頼でき、管理しやすく、低コストなサイトにつながります&mdash;特に大規模環境ではそうです。この半技術的な文書では、ソフトウェアエンジニアリングによってその目標をどのように実現しているかを説明します。


<a id="overview"></a>
## 概要

Caddy は、コマンド、コアライブラリ、モジュールで構成されています。

**コマンド** は、あなたがよく知っているであろう [command line interface](/docs/command-line) を提供します。これは、オペレーティングシステムからプロセスを起動する方法です。ここにあるコードとロジックはかなり少なく、ユーザーが望む方法でコアをブートストラップするために必要なものだけを含みます。設定については、ブートストラップに関係する場合を除き、フラグや環境変数の使用を意図的に避けています。


<aside class="tip">

モジュールは command line interface にサブコマンドを追加できます。たとえば、[`caddy file-server`](/docs/command-line#caddy-file-server) コマンドはそこから来ています。追加されたコマンドは、コアの Caddy コマンドがフラグや環境変数の使用を最小限にしている場合でも、必要なフラグや環境変数を自由に使えます。

</aside>


**[コアライブラリ](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc)**、つまり Caddy の「コア」は、主に設定を管理します。新しい設定を [`Run()`](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Run) したり、実行中の設定を [`Stop()`](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Stop) したりできます。また、モジュールが使うための各種ユーティリティ、型、値も提供します。

**モジュール** はそれ以外のすべてを行います。多くのモジュールは Caddy に組み込まれており、これらは *標準モジュール* と呼ばれます。これは、最も多くのユーザーにとって最も有用だと判断されたものです。


<aside class="tip">

*module*、*plugin*、*extension* という用語が同じ意味で使われることがありますが、たいていは問題ありません。技術的には、すべてのモジュールはプラグインですが、すべてのプラグインがモジュールというわけではありません。モジュールは、Caddy の [設定構造](/docs/json/) を拡張する特定の種類のプラグインです。

</aside>




<a id="caddy-core"></a>
## Caddy コア

Caddy のコアが行うことは、基本的には初期設定（"config"）を読み込むこと、または初期設定がない場合に後で新しい設定を受け付けるためのソケットを開くことだけです。

[Caddy の設定](/docs/json/) は JSON 文書で、トップレベルにいくつかのフィールドがあります。

```json
{
	"admin": {},
	"logging": {},
	"apps": {•••},
	...
}
```

Caddy のコアは、これらのフィールドの一部をネイティブに扱う方法を知っています。

- [`admin`](/docs/json/admin/) は、[admin API](/docs/api) をセットアップし、プロセスを管理するためです
- [`logging`](/docs/json/logging/) は、[ログを出力](/docs/logging) するためです

しかし、他のトップレベルフィールド（たとえば [`apps`](/docs/json/apps/)）は、Caddy のコアにとっては不透明です。実際、Caddy が `apps` のバイト列に対して知っていることは、それをインターフェイス型にデシリアライズし、その上で 2 つのメソッドを呼べるということだけです。

1. `Start()`
2. `Stop()`

... それだけです。設定が読み込まれると各 app に対して `Start()` を呼び、設定がアンロードされると各 app に対して `Stop()` を呼びます。

app モジュールが開始されると、その app のモジュールライフサイクルが始まります。


<aside class="tip">

Caddy モジュールを作っているプログラマーであれば、同様の情報を [Extending Caddy](/docs/extending-caddy) ガイドで見つけられます。ただし、そちらはコードにより重点を置いています。

</aside>


<a id="module-lifecycle"></a>
## モジュールライフサイクル

モジュールには、*host modules* と *guest modules* の 2 種類があります。

**Host modules**（または「親」モジュール）は、他のモジュールを読み込むモジュールです。

**Guest modules**（または「子」モジュール）は、読み込まれるモジュールです。すべてのモジュールは guest modules です。app モジュールでさえそうです。

モジュールは、次の順序で読み込まれ、プロビジョニングと検証を受け、使用され、最後にクリーンアップされます。

1. 読み込み
2. プロビジョニングと検証
3. 使用
4. クリーンアップ

Caddy は、設定が最初に読み込まれたとき、設定されたすべての app モジュールを初期化してモジュールライフサイクルを開始します。そこからは、各 app モジュールが残りの処理を引き継ぎ、下位のモジュールへと連鎖していきます。

<a id="load-phase"></a>
### 読み込みフェーズ

モジュールの読み込みとは、その JSON バイト列をメモリ上の型付きの値へデシリアライズすることです。つまり... 基本的にはそれだけです。JSON を値へデコードしているだけです。

<a id="provision-phase"></a>
### プロビジョニングフェーズ

このフェーズでは、セットアップ作業の大部分が行われます。すべてのモジュールは、読み込まれた後に自分自身をプロビジョニングする機会を持ちます。

JSON エンコード由来のプロパティはすでにデコードされているため、ここで必要なのは追加のセットアップだけです。プロビジョニング中の最も一般的な作業は、guest modules のセットアップです。言い換えると、host module のプロビジョニングは、その guest modules のプロビジョニングも引き起こし、それが下位まで続きます。

これは、[ドキュメント内で Caddy の JSON 構造をたどる](/docs/json/) と感覚をつかめます。`{•••}` が表示される場所では guest modules を使える可能性があり、そこをクリックしていくと、guest modules がなくなるまで下位へ探索できます。

その他の一般的なプロビジョニング作業には、モジュールの存続期間中に使用する内部値のセットアップや、入力の標準化があります。たとえば、[`http.matchers.remote_ip`](/docs/modules/http.matchers.remote_ip) モジュールは、JSON から受け取った文字列入力から CIDR 値を解析するためにプロビジョニングフェーズを使います。こうすることで、HTTP リクエストごとにこの処理を行う必要がなくなり、結果として効率が上がります。

検証もプロビジョニングフェーズで行えます。モジュールの最終的な設定が無効であれば、ここでエラーを返し、設定全体の読み込み処理を中止できます。

<a id="use-phase"></a>
### 使用フェーズ

guest module がプロビジョニングされ検証されると、host module から使用できるようになります。これが具体的に何を意味するかは、各 host module によって決まります。

各モジュールには ID があり、これは namespace と、その namespace 内の name で構成されます。たとえば、[`http.handlers.reverse_proxy`](/docs/modules/http.handlers.reverse_proxy) は `http.handlers` namespace にあり、name が `reverse_proxy` なので、HTTP handler です。`http.handlers` namespace のすべてのモジュールは、host module が知っている同じインターフェイスを満たします。そのため、`http` app はこれらの種類のモジュールを読み込み、使用する方法を知っています。

<a id="cleanup-phase"></a>
### クリーンアップフェーズ

設定を停止する時期になると、すべてのモジュールがアンロードされます。モジュールが解放すべきリソースを確保していた場合、このクリーンアップフェーズでそれを行う機会があります。


<a id="plugging-in"></a>
## 組み込み

モジュール、または任意の Caddy プラグインは、そのモジュールのパッケージに対する `import` を追加することで Caddy に「組み込まれ」ます。パッケージを import すると、[モジュールは Caddy コアに自分自身を登録](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#RegisterModule) するため、Caddy プロセスが起動したときに、各モジュールを名前で認識できます。モジュールの値と名前を相互に関連付けることさえできます。


<aside class="tip">

プラグインは、Caddy のコードベースをまったく変更せずに追加できます。その方法は [readme](https://github.com/caddyserver/caddy/#with-version-information-andor-plugins) に説明があります。

</aside>


<a id="managing-configuration"></a>
## 設定の管理

実行中サーバーのアクティブな設定を変更すること（よく「reload」と呼ばれます）は、サーバーが必要とする高い並行性と数千ものパラメーターのため、難しくなりがちです。Caddy は、多くの利点を持つ設計によってこの問題をエレガントに解決しています。

- 実行中サービスを中断しない
- 粒度の細かい設定変更が可能
- 必要なロックは 1 つだけ（バックグラウンドで）
- すべての reload は atomic、consistent、isolated、かつほぼ durable（"ACID"）
- グローバル状態を最小限にする

[Caddy 2 の設計についての動画はこちら](https://www.youtube.com/watch?v=EhJO8giOqQs) で見られます。

設定の reload は、新しいモジュールをプロビジョニングし、すべて成功したら古いモジュールをクリーンアップすることで動作します。短い間、2 つの設定が同時に稼働します。

各設定は、すべてのモジュール状態を保持する [context](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Context) に関連付けられています。そのため、ほとんどの状態は設定のスコープ外に出ません。これは正確性、性能、単純さにとって良いことです。

ただし、本当にグローバルな状態が必要になる場合もあります。たとえば、reverse proxy は upstream の健全性を追跡することがあります。各 upstream はグローバルに 1 つだけなので、小さな設定変更のたびにそれを忘れてしまうのは望ましくありません。幸い、Caddy はグローバル状態を整理して保つために、言語ランタイムのガベージコレクターに似た [機能](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#UsagePool) を提供しています。

オンラインで設定を更新する明白な方法の 1 つは、すべての設定パラメーターへのアクセスを、ホットパスでさえ同期することです。これは性能と複雑さの面で信じられないほど悪い方法です&mdash;特に大規模環境ではそうです&mdash;そのため Caddy はこの方法を使いません。

代わりに、設定は不変で atomic な単位として扱われます。全体が置き換えられるか、何も変更されないかのどちらかです。[admin API endpoints](/docs/api)&mdash;構造をたどって粒度の細かい変更を許可するもの&mdash;は、メモリ上の設定表現だけを変更し、そこからまったく新しい設定文書を生成して読み込みます。この方法は、単純さ、性能、一貫性の面で大きな利点があります。ロックが 1 つだけなので、Caddy は連続した reload を簡単に処理できます。
