<a id="how-logging-works"></a>
ログの仕組み
=================

Caddy には強力で柔軟なロギング機能があります。ただし、従来型の共有ホスティングや古い Web サーバーに慣れている場合は、期待しているものと少し違って見えるかもしれません。


<a id="overview"></a>
## 概要

ロギングには主に 2 つの側面があります。発行と消費です。

**発行** とは、メッセージを生成することです。これは 3 つの手順で構成されます。

1. 関連情報を集める（コンテキスト）
2. 役立つ表現を組み立てる（エンコード）
3. その表現を出力へ送る（書き込み）

この機能は Caddy のコアに組み込まれているため、Caddy のコードベースやモジュール（プラグイン）のどの部分からでもログを発行できます。

**消費** とは、メッセージを取り込み、処理することです。発行されたログが役立つには、消費される必要があります。書き込まれただけで誰にも読まれないログには価値がありません。ログの消費は、管理者がコンソール出力を読むだけの簡単なものから、ログ集約ツールやクラウドサービスを接続してログメッセージをフィルタリング、集計、インデックス化する高度なものまであります。

<a id="caddys-role"></a>
### Caddy の役割

*Caddy はログ発行者です*。Caddy はログを消費しません。ただし、ログをエンコードして書き込むために必要な最小限の処理は行います。これは重要です。Caddy のコアをより単純に保ち、バグやエッジケースを減らし、保守負荷を下げられるからです。最終的に、ログ処理は Caddy コアの範囲外です。

ただし、ログを消費する Caddy アプリモジュールが存在する可能性はあります。（私たちの知る限り、まだ存在していないだけです。）


<a id="structured-logs"></a>
## 構造化ログ

多くの現代的なアプリケーションと同じく、Caddy のログは *構造化* されています。つまり、メッセージ内の情報は単なる不透明な文字列やバイト列ではありません。代わりに、メッセージをエンコードして書き出す時点まで、データは強く型付けされ、個別の *フィールド名* によってキー付けされています。

従来の HTTP サーバーでよく使われる、古い Common Log Format（CLF）のような非構造化ログと比べてみましょう。

```
127.0.0.1 - - [10/Oct/2000:13:55:36 -0700] "GET /apache_pb.gif HTTP/1.1" 200 2326
```

この形式には「構造」はありますが、「構造化」されてはいません。HTTP リクエストを記録することにしか使えません。不透明なバイト文字列なので、別の形式へ効率よくエンコードする方法もありません。さらに、多くの情報が欠けています。リクエストの Host header すら含まれていません。このログ形式は、単一サイトをホストしていて、リクエストについてごく基本的な情報だけを得たい場合にしか役立ちません。

<aside class="tip">
	CLF にホスト情報がないため、複数サイトをホストする場合、通常これらのログはサイトごとに別ファイルへ書き込む必要があります。そうしなければ、リクエストから Host header を知る方法がないからです。
</aside>

次に、Caddy の同等の構造化ログメッセージを見てみましょう。JSON としてエンコードし、表示しやすいように整形したものです。

```json
{
	"level": "info",
	"ts": 1646861401.5241024,
	"logger": "http.log.access",
	"msg": "handled request",
	"request": {
		"remote_ip": "127.0.0.1",
		"remote_port": "41342",
		"client_ip": "127.0.0.1",
		"proto": "HTTP/2.0",
		"method": "GET",
		"host": "localhost",
		"uri": "/",
		"headers": {
			"User-Agent": ["curl/7.82.0"],
			"Accept": ["*/*"],
			"Accept-Encoding": ["gzip, deflate, br"],
		},
		"tls": {
			"resumed": false,
			"version": 772,
			"cipher_suite": 4865,
			"proto": "h2",
			"server_name": "example.com"
		}
	},
	"bytes_read": 0,
	"user_id": "",
	"duration": 0.000929675,
	"size": 10900,
	"status": 200,
	"resp_headers": {
		"Server": ["Caddy"],
		"Content-Encoding": ["gzip"],
		"Content-Type": ["text/html; charset=utf-8"],
		"Vary": ["Accept-Encoding"]
	}
}
```

構造化ログの方がはるかに有用で、はるかに多くの情報を含んでいることが分かります。このログメッセージの豊富な情報は有用なだけでなく、実質的に性能上のオーバーヘッドもありません。Caddy のログはゼロアロケーションです。構造化ログはデータ型やコンテキストに制限がなく、どのコードパスでも使え、どのような情報でも含められます。

ログは構造化され、強く型付けされているため、任意の形式にエンコードできます。JSON を扱いたくない場合でも、ログを別の表現にエンコードできます。Caddy は [ログエンコーダーモジュール](/docs/json/logging/logs/encoder/)を通じて他の形式をサポートしており、さらに追加することもできます。

構造化ログと従来形式の違いで **最も重要** なのは、性能上のコストを払えば構造化ログは[従来の Common Log Format へ変換できます <img src="/old/resources/images/external-link.svg" class="external-link">](https://github.com/caddyserver/transform-encoder)が、その逆はできないという点です。CLF から構造化形式へ変換するのは簡単ではなく（少なくとも非効率であり）、情報が欠けていることを考えると不可能です。

要するに、効率的な構造化ロギングは一般に次の考え方を促します。

- ログが少なすぎるより、多すぎる方がよい
- 捨てるより、フィルタリングする方がよい
- 柔軟性と相互運用性のために、エンコードは遅らせる
 

<a id="emission"></a>
## 発行

コード内でのログ発行は、次のような形になります。

```go
logger.Debug("proxy roundtrip",
	zap.String("upstream", di.Upstream.String()),
	zap.Object("request", caddyhttp.LoggableHTTPRequest{Request: req}),
	zap.Object("headers", caddyhttp.LoggableHTTPHeader(res.Header)),
	zap.Duration("duration", duration),
	zap.Int("status", res.StatusCode),
)
```

<aside class="tip">
	これは Caddy の reverse proxy に実際にあるコード行です。この行により、debug ログを有効にしているとき、設定済み upstream へのリクエストを調べられます。トラブルシューティングでは非常に貴重なデータです。
</aside>

この 1 回の関数呼び出しに、ログレベル、メッセージ、複数のデータフィールドが含まれていることが分かります。これらはすべて強く型付けされており、Caddy はゼロアロケーションのロギングライブラリを使うため、ログ発行は高速で効率的であり、オーバーヘッドはほとんどありません。

`logger` 変数は `zap.Logger` で、任意の量のコンテキストを関連付けられます。これには名前とデータフィールドの両方が含まれます。そのため、ロガーは親コンテキストから自然に「継承」でき、高度なトレースやメトリクスが可能になります。

そこからメッセージは高効率な処理パイプラインへ送られ、エンコードされ、書き込まれます。


<a id="logging-pipeline"></a>
## ロギングパイプライン

上で見たように、メッセージは **ロガー** によって発行されます。その後、メッセージは処理のために **ログ** へ送られます。

Caddy では、メッセージを処理する[複数のログを設定](/docs/json/logging/logs/)できます。ログは、エンコーダー、ライター、最小レベル、サンプリング比率、含めるまたは除外するロガーのリストで構成されます。Caddy には常に `default` という名前の既定ログがあります。設定内の[このオブジェクト](/docs/json/logging/logs/)で `"default"` をキーにしたログを指定すると、これをカスタマイズできます。

<aside class="tip">

ここで [Caddy のロギングドキュメント](/docs/json/logging/)を確認し、ここで説明している構造やパラメータに慣れておくとよいでしょう。

</aside>


- **エンコーダー:** ログの形式です。メモリ内のデータ表現をバイト列へ変換します。エンコーダーはログメッセージのすべてのフィールドにアクセスできます。
- **ライター:** ログの出力先です。ファイルやネットワークソケットなど、任意のログライターモジュールを使えます。単にバイトを書き込みます。
- **レベル:** ログには DEBUG から FATAL まで複数のレベルがあります。指定レベルより低いメッセージは、そのログでは無視されます。
- **サンプリング:** 非常に高頻度なパスでは、効果的に処理できる量を超えるログが発行されることがあります。サンプリングを有効にすると、代表的なメッセージのサンプルを維持しながら負荷を下げられます。
- **Include/exclude:** 各メッセージは、名前を持つロガーから発行されます（通常はモジュール ID から派生します）。ログは特定ロガーからのメッセージを含めたり除外したりできます。

Caddy からログメッセージが発行されると、次の流れになります。

- 発行元ロガーの名前が各ログの include/exclude リストと照合され、含まれる（または除外されない）場合、そのログへ取り込まれます。
- サンプリングが有効な場合、簡単な計算でそのログメッセージを保持するか決めます。
- メッセージは、そのログに設定されたエンコーダーでエンコードされます。
- エンコード済みバイト列は、そのログに設定されたライターへ書き込まれます。

既定では、すべてのメッセージが設定済みのすべてのログへ送られます。これは上で説明した構造化ロギングの価値観に沿っています。include/exclude リストを設定すれば、どのメッセージをどのログへ送るか制限できますが、これは主に異なるモジュールからのメッセージをフィルタリングするためのものです。ログ集約サービスのように使うことは意図していません。Caddy のロギングパイプラインを簡潔で効率的に保つため、ログメッセージの高度な処理は消費側に委ねられます。

<a id="consumption"></a>
## 消費

メッセージが出力へ送られた後、コンシューマーがそれを読み込み、解析し、適切に扱います。

これはログ発行とはまったく別の問題領域であり、Caddy のコアは消費を扱いません（もちろん Caddy アプリモジュールで実装することは可能です）。JSON メッセージ（または他の形式）のストリームを処理し、ログを表示、フィルタリング、インデックス化、検索するためのツールは数多くあります。自分で書いたり実装したりすることもできます。

たとえば、特定のフィールド（例: ホスト名）に基づいて CLF を別ファイルへ分ける必要があるレガシーソフトウェアを実行している場合、JSON を読み込み、`sprintf()` を呼んで CLF 文字列を作り、`request.host` フィールドの値に基づいてファイルへ書き込む簡単なツールを使う、または書くことができます。

Caddy のロギング機能は、メトリクスやトレースの実装にも使えます。メトリクスは基本的に特定の特徴を持つメッセージを数え、トレースは複数のメッセージをそれらの共通点に基づいて結び付けます。

Caddy のログを消費することで、できることは無数にあります。
