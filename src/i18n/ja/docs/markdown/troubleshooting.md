<a id="troubleshooting-strategies"></a>
トラブルシューティング戦略
=====================

このページでは、Caddy を使うときに遭遇する多くの問題を、*AI を使わずに* 自力で修正するための一般的で体系的な枠組みを紹介します。フォーラムで助けを求めるときにも、同じような手順をおすすめしています。多くの場合、批判的に考えることで、自分の質問に自分で答えたり、自分で問題を修正したりできます。


<a id="what-do-you-know"></a>
分かっていることは何か？
-----------------

何が問題なのか、何が原因なのか、どう直せばよいのか分からないかもしれません。そこで、確実に分かっている基本的なことから始めましょう。

<a id="what-you-expect"></a>
### 期待する動作

声に出す、頭の中で言う、または書き出してください。疑問や曖昧さが残らないように、明確かつ具体的にします。なぜそれを期待するのかを自分に説明してもよいでしょう。

「動くはず」は、よい期待ではありません。

「この URI にリクエストしたとき、301 リダイレクトを期待している」の方がずっとよいです。


<a id="current-behavior"></a>
### 現在の動作

何が起きているかを観察します。*正確には* 何が起きていて、それは期待とどう違うのでしょうか。分かっていることを整理してください。

「動かない」は役に立たず、怠惰な表現です。すでに詳細に記録された具体的な動作を短く指す場合を除き、どこでも避けてください。

「301 レスポンスではなく 200 レスポンスが返っている。ただし `Server: Caddy` header は見えている」の方がずっとよいです。これは、分かっていることと期待していることを比較し、他の既知情報も整理しています。つまり、リクエストが少なくとも Caddy インスタンスには到達していることが分かります。


<a id="logs"></a>
### ログ

Caddy のログには何が出ていますか。既定では、ログはプロセスを起動したターミナルへ書き込まれます。systemd サービスのように「デタッチ」して実行している場合は、別の場所からログを取得する必要があるかもしれません。

HTTP リクエストログ（「アクセスログ」）はプロセスログとは別物であり、設定で明示的に有効化する必要があります。

まだ有効にしていない場合は、DEBUG レベルのロギングを有効にしてもよいでしょう。

いずれにしても、最初にやるべきことの 1 つはログを見ることです。*すべてのログを* 見てください。メッセージのコンテキストは重要なので、単独のログ行だけではほとんど役に立ちません。必要だと思う量より多めに集め、トラブルシューティングの間は保持してください。

ログに手がかりはありますか。


<a id="recognize-and-doubt-assumptions"></a>
前提を認識し、疑う
-------------------------------

先へ進む前に、前提を批判的に見ることがどれほど重要かを強調しておきます。私たちは皆、慣れているものや期待しているものに基づいて前提を置きます。「自分の前提に注意せよ。そうすれば大きな力を得るだろう。」（&mdash;Yoda、またはそのような何か。）

たとえば、よくある前提として、Caddy を再コンパイルした後に `caddy` を実行すれば新しいコードが動く、というものがあります。これは、コンパイルしたバイナリが `$PATH` 内のものを置き換えた場合にだけ正しいです。通常は `./caddy` が適切な呼び出しです。

デプロイや設定が複雑になるほど、前提は積み重なります。たとえば Docker でデプロイする場合、イメージを再ビルドして実行する必要があり、そこで置く前提も増えます。

多くの質問やバグ報告は、Caddy 自体ではなく、外部システムやネットワーク設定の問題に行き着きます。たとえば Caddy インスタンスへ接続できないが、Caddy は明らかに動作している場合、DNS ではないと考えがちです。ヒント: ほとんどの場合 DNS です。

設定をリロードしたつもりでも、実際にはしていなかった、というだけでもよくあるミスです。手順には厳密であるよう努めてください。すべての段階で検証しましょう。


<a id="reproduce-the-behavior"></a>
動作を再現する
----------------------

これは重要な手順であり、この過程で問題が自然に解決することもよくあります。問題をもう一度発生させてください。

具体的には、*できるだけ最小の形で* 発生させます。不要な設定、デプロイ手順、環境要因などを取り除き、問題が消えるまで減らします。

一般的な方法は、1 回に 1 つだけ取り除いて再試行し、問題が消えるまで続けることです。すると、最後に取り除いたものが原因である可能性が高いです。あるいは、ここで前提を疑うべきですが、最後のものとその前に取り除いたものの組み合わせが原因かもしれません。最初に取り除いたものを戻して検証してください。範囲を絞り込みます。

別の方法として、各反復で全体の約半分を取り除き、問題が消えたらその半分のさらに半分を取り除く、というやり方もあります。これは二分探索のようなもので、より速いことがあります。

逆に、削除ではなく、設定やシナリオをゼロから少しずつ組み立て、毎回再試行しながら、問題が現れるまで進めることもできます。

多くの場合、このプロセスだけで問題が特定され、修正方法も明らかになります。そうでなくても、少なくとも問題を再現するための最小手順を書き出せます。


<a id="explore-behaviors"></a>
動作を調べる
-----------------

問題を再現する手順が分かったら、原因を診断しやすい状態です。ここでは試行錯誤し、詳しければコードも読みます。

なぜ問題が起きているのか説明できない場合は、動作を変えてみてください。小さな変更を加えて再試行します。たとえば関連する設定に正規表現があるなら、その式を変更または簡略化する、あるいは完全に削除して、期待する動作に近づく *何か* が起きるか見てください。望んだ通りでなくても、少なくとも問題が正規表現または設定にあることは分かります。

調査しながら、何がうまくいき、何がうまくいかないかのパターンに注意してください。それが解決策へ向かう道筋になります。

解決策が見つかったら、それがバグとして扱うべきものか判断できます。バグかどうか明らかでないこともあります。その場合は、実験内容を添えて issue を投稿し、どちらにせよメンテナーのフィードバックを得ても構いません。

もしバグでなければ、おめでとうございます。あなたは問題を解決し、その過程で少なくとも何かを学びました。

同じ問題に遭遇するかもしれない他の人のために、経験を[フォーラム](https://caddy.community)へ投稿することも検討してください。
