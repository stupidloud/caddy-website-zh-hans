<a id="architecture"></a>아키텍처
============

Caddy는 Go로 작성되었기 때문에 외부 종속성이 없는 단일하고 독립적인 정적 바이너리입니다. 이러한 가치들은 배포를 단순화하고 프로덕션 환경에서의 지루한 문제 해결을 줄여주기 때문에 프로젝트 비전의 중요한 부분을 구성합니다.

동적 링킹이 없다면 어떻게 확장할 수 있을까요? Caddy는 외부(동적으로 연결된) 종속성이 있는 웹 서버를 포함하여 다른 어떤 웹 서버보다 그 기능을 훨씬 더 확장할 수 있는 새로운 플러그인 아키텍처를 특징으로 합니다.

"움직이는 부품을 적게" 하자는 우리의 철학은 궁극적으로 더욱 안정적이고 관리하기 쉬우며 덜 비싼 사이트(특히 대규모에서)를 결과로 가져옵니다. 이 반(半) 기술적인 문서는 소프트웨어 엔지니어링을 통해 우리가 그 목표를 어떻게 달성하는지 설명합니다.


## <a id="overview"></a>개요

Caddy는 명령, 핵심 라이브러리, 그리고 모듈로 구성됩니다.

**명령(command)** 은 여러분에게 친숙할 [명령줄 인터페이스](/docs/command-line)를 제공합니다. 운영 체제에서 프로세스를 시작하는 방법입니다. 여기의 코드와 논리 양은 상당히 최소화되어 있으며, 사용자가 원하는 방식으로 코어를 부트스트랩하는 데 필요한 것만 가지고 있습니다. 부트스트랩 구성과 관련되지 않는 한 구성을 위해 플래그와 환경 변수를 사용하는 것을 의도적으로 피합니다.


<aside class="tip">

모듈은 명령줄 인터페이스에 하위 명령을 추가할 수 있습니다! 예를 들어, [`caddy file-server`](/docs/command-line#caddy-file-server) 명령이 바로 여기서 나옵니다. 이러한 추가된 명령은 코어 Caddy 명령이 사용을 최소화하더라도 원하는 플래그나 환경 변수를 사용할 수 있습니다.

</aside>


**[핵심 라이브러리(core library)](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc)**, 또는 Caddy의 "코어(core)"는 주로 구성을 관리합니다. 새 구성을 [`Run()`](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Run)하거나 실행 중인 구성을 [`Stop()`](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Stop)할 수 있습니다. 또한 모듈이 사용할 수 있는 다양한 유틸리티, 유형 및 값을 제공합니다.

**모듈(Modules)** 은 그 밖의 모든 것을 수행합니다. 많은 모듈이 Caddy에 내장되어 제공되며, 이를 *표준 모듈*이라고 합니다. 이들은 대부분의 사용자에게 가장 유용한 것으로 결정된 것들입니다.


<aside class="tip">

때로는 *모듈*, *플러그인*, *확장*이라는 용어가 상호 교환적으로 사용되며, 보통은 그래도 괜찮습니다. 엄밀히 말하면 모든 모듈은 플러그인이지만 모든 플러그인이 모듈인 것은 아닙니다. 모듈은 특별히 Caddy의 [구성 구조](/docs/json/)를 확장하는 플러그인의 한 종류입니다.

</aside>




## <a id="caddy-core"></a>Caddy 코어

핵심적으로 Caddy는 단지 초기 구성("config")을 로드하거나, 구성이 없는 경우 나중에 새 구성을 허용하기 위해 소켓을 엽니다.

[Caddy 구성](/docs/json/)은 최상위 수준에 몇 가지 필드가 있는 JSON 문서입니다:

```json
{
	"admin": {},
	"logging": {},
	"apps": {•••},
	...
}
```

Caddy의 코어는 이러한 필드 중 일부를 기본적으로 다루는 방법을 알고 있습니다:

- [`admin`](/docs/json/admin/) 그래서 [관리자 API](/docs/api)를 설정하고 프로세스를 관리할 수 있습니다.
- [`logging`](/docs/json/logging/) 그래서 [로그를 생성](/docs/logging)할 수 있습니다.

하지만 다른 최상위 필드(예: [`apps`](/docs/json/apps/))는 Caddy의 코어에게 불투명합니다. 사실, Caddy가 `apps`의 바이트를 가지고 할 줄 아는 것은 두 가지 메서드를 호출할 수 있는 인터페이스 유형으로 역직렬화하는 것뿐입니다:

1. `Start()`
2. `Stop()`

... 그게 전부입니다. 구성이 로드될 때 각 앱에서 `Start()`를 호출하고 구성이 언로드될 때 각 앱에서 `Stop()`을 호출합니다.

앱 모듈이 시작되면 앱의 모듈 수명 주기가 시작됩니다.


<aside class="tip">

Caddy 모듈을 빌드하는 프로그래머라면 코드에 더 중점을 둔 [Caddy 확장](/docs/extending-caddy) 가이드에서 유사한 정보를 찾을 수 있습니다.

</aside>


## <a id="module-lifecycle"></a>모듈 수명 주기

모듈에는 *호스트 모듈*과 *게스트 모듈*의 두 종류가 있습니다.

**호스트 모듈(Host modules)**(또는 "부모" 모듈)은 다른 모듈을 로드하는 모듈입니다.

**게스트 모듈(Guest modules)**(또는 "자식" 모듈)은 로드되는 모듈입니다. 앱 모듈을 포함한 모든 모듈은 게스트 모듈입니다.

모듈은 다음 순서로 로드되고, 프로비저닝 및 검증되며, 사용된 후 정리됩니다:

1. 로드 (Loaded)
2. 프로비저닝 및 검증 (Provisioned and validated)
3. 사용 (Used)
4. 정리 (Cleaned up)

Caddy는 구성이 처음 로드될 때 구성된 모든 앱 모듈을 초기화하여 모듈 수명 주기를 시작합니다. 그 후 각 앱 모듈이 나머지 과정을 진행하면서 끝까지 이어집니다.

### <a id="load-phase"></a>로드 단계

모듈을 로드하는 과정에는 JSON 바이트를 메모리의 타입이 있는 값으로 역직렬화하는 작업이 포함됩니다. 이것이... 기본적으로 전부입니다. 단지 JSON을 값으로 디코딩하는 것입니다.

### <a id="provision-phase"></a>프로비저닝 단계

이 단계는 설정 작업의 대부분이 수행되는 곳입니다. 모든 모듈은 로드된 후 자신을 프로비저닝할 기회를 얻습니다.

JSON 인코딩의 속성은 이미 디코딩되었으므로 여기서는 추가 설정만 수행하면 됩니다. 프로비저닝 중 가장 일반적인 작업은 게스트 모듈을 설정하는 것입니다. 즉, 호스트 모듈을 프로비저닝하면 그 하위의 모든 게스트 모듈도 프로비저닝됩니다.

[문서에서 Caddy의 JSON 구조를 탐색](/docs/json/)하여 이에 대한 감을 잡을 수 있습니다. `{•••}`가 보이는 모든 곳에서 게스트 모듈이 사용될 수 있으며, 그중 하나를 클릭하면 더 이상 게스트 모듈이 없을 때까지 계속 탐색할 수 있습니다.

다른 일반적인 프로비저닝 작업으로는 모듈의 수명 동안 사용될 내부 값을 설정하거나 입력을 표준화하는 것이 있습니다. 예를 들어, [`http.matchers.remote_ip`](/docs/modules/http.matchers.remote_ip) 모듈은 프로비저닝 단계를 사용하여 JSON에서 받은 문자열 입력에서 CIDR 값을 구문 분석합니다. 이렇게 하면 모든 HTTP 요청마다 이 작업을 수행할 필요가 없어 결과적으로 더 효율적입니다.

프로비저닝 단계에서 검증도 수행할 수 있습니다. 모듈의 결과 구성이 유효하지 않은 경우, 여기서 오류를 반환하여 전체 구성 로드 프로세스를 중단시킬 수 있습니다.

### <a id="use-phase"></a>사용 단계

게스트 모듈이 프로비저닝되고 검증되면 호스트 모듈에서 이를 사용할 수 있습니다. 이것이 정확히 무엇을 의미하는지는 각 호스트 모듈에 달려 있습니다.

각 모듈에는 네임스페이스와 해당 네임스페이스 내의 이름으로 구성된 ID가 있습니다. 예를 들어, [`http.handlers.reverse_proxy`](/docs/modules/http.handlers.reverse_proxy)는 `http.handlers` 네임스페이스에 속하고 이름이 `reverse_proxy`이므로 HTTP 핸들러입니다. `http.handlers` 네임스페이스의 모든 모듈은 호스트 모듈에 알려진 동일한 인터페이스를 충족합니다. 따라서 `http` 앱은 이러한 종류의 모듈을 로드하고 사용하는 방법을 알고 있습니다.

### <a id="cleanup-phase"></a>정리 단계

구성을 중지할 때가 되면 모든 모듈이 언로드됩니다. 모듈이 해제해야 할 리소스를 할당한 경우, 이 정리 단계에서 해제할 기회가 있습니다.


## <a id="plugging-in"></a>플러그인 연결

모듈(또는 Caddy 플러그인)은 모듈의 패키지에 대한 `import`를 추가하여 Caddy에 "연결(plugged in)"됩니다. 패키지를 가져옴으로써 [모듈은 자신을 Caddy 코어에 등록](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#RegisterModule)하므로 Caddy 프로세스가 시작될 때 각 모듈을 이름으로 알 수 있습니다. 심지어 모듈 값과 이름 간의 연관성도 맺을 수 있습니다.


<aside class="tip">

Caddy 코드 기반을 전혀 수정하지 않고도 플러그인을 추가할 수 있습니다. 이 작업을 수행하기 위한 지침이 [추가 정보(readme)에 있습니다](https://github.com/caddyserver/caddy/#with-version-information-andor-plugins)!

</aside>


## <a id="managing-configuration"></a>구성 관리

실행 중인 서버의 활성 구성 변경(종종 "새로 고침(reload)"이라고 함)은 서버가 요구하는 높은 수준의 동시성과 수천 개의 매개변수 때문에 까다로울 수 있습니다. Caddy는 다음과 같은 많은 이점이 있는 설계를 통해 이 문제를 우아하게 해결합니다:

- 실행 중인 서비스 중단 없음
- 세분화된 구성 변경 가능
- 하나의 잠금(lock)만 필요 (백그라운드에서)
- 모든 새로 고침은 원자적이고 일관되며 격리되어 있고 대부분 내구성이 있음 ("ACID")
- 최소한의 전역 상태

[여기서 Caddy 2 설계에 대한 영상을 시청할 수 있습니다](https://www.youtube.com/watch?v=EhJO8giOqQs).

구성 새로 고침은 새 모듈을 프로비저닝하여 작동하며, 모두 성공하면 이전 모듈이 정리됩니다. 짧은 시간 동안 두 개의 구성이 동시에 작동합니다.

각 구성은 모든 모듈 상태를 보유하는 [컨텍스트](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Context)와 연결되므로 대부분의 상태는 구성 범위를 벗어나지 않습니다. 이는 정확성, 성능, 단순성 측면에서 좋은 소식입니다!

하지만 때로는 진정한 전역 상태가 필요합니다. 예를 들어 역방향 프록시는 업스트림의 상태를 추적할 수 있습니다. 각 업스트림은 전역적으로 하나뿐이므로, 사소한 구성 변경이 있을 때마다 이를 잊어버리면 문제가 될 것입니다. 다행히 Caddy는 언어 런타임의 가비지 수집기와 유사한 [기능을 제공](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#UsagePool)하여 전역 상태를 깔끔하게 유지합니다.

온라인 구성 업데이트에 대한 명확한 접근 방식 중 하나는 중요한 경로(hot path)에서도 모든 단일 구성 매개변수에 대한 접근을 동기화하는 것입니다. 이는 성능 및 복잡성 측면에서—특히 대규모일 때—믿을 수 없을 정도로 나쁘기 때문에 Caddy는 이 접근 방식을 사용하지 않습니다.

대신 구성을 불변하는 원자적 단위로 취급합니다. 전체를 교체하거나 아무것도 변경하지 않습니다. [관리자 API 엔드포인트](/docs/api) (구조를 탐색하여 세분화된 변경을 허용)는 구성의 메모리 내 표현만 변경하며, 여기에서 완전히 새로운 구성 문서가 생성되고 로드됩니다. 이 접근 방식은 단순성, 성능, 일관성 측면에서 방대한 이점이 있습니다. 잠금이 하나뿐이므로 Caddy는 빠른 새로 고침을 처리하기 쉽습니다.
