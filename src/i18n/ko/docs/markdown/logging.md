로깅 작동 방식
=================

Caddy에는 강력하고 유연한 로깅 기능이 있지만, 특히 더 오래된 공유 호스팅이나 다른 레거시 웹 서버에서 오신 분들이라면 익숙했던 방식과 다를 수 있습니다.


## 개요

로깅에는 생성(emission)과 소비(consumption)라는 두 가지 주요 측면이 있습니다.

**생성(Emission)은** 메시지를 생성하는 것을 의미합니다. 세 단계로 구성됩니다:

1. 관련 정보(컨텍스트) 수집
2. 유용한 표현(인코딩) 구축
3. 해당 표현을 출력으로 보내기(쓰기)

이 기능은 Caddy의 핵심에 내장되어 있어 Caddy 코드 베이스의 모든 부분 또는 모듈(플러그인)이 로그를 내보낼 수 있도록 합니다.

**소비(Consumption)는** 메시지의 수집 및 처리입니다. 유용하기 위해서는 내보낸 로그를 소비해야 합니다. 그저 쓰여지기만 하고 읽히지 않는 로그는 가치가 없습니다. 로그 소비는 관리자가 콘솔 출력을 읽는 것처럼 간단할 수도 있고, 로그 집계 도구나 클라우드 서비스를 연결하여 로그 메시지를 필터링, 계산 및 색인화하는 것처럼 고급일 수도 있습니다.

### Caddy의 역할

*Caddy는 로그 생성기입니다.* 로그를 인코딩하고 쓰는 데 필요한 최소한의 처리 외에는 로그를 소비하지 않습니다. 이는 유지 관리 부담을 줄이면서 Caddy의 핵심을 더 단순하게 유지하여 버그와 엣지 케이스를 줄여주기 때문에 중요합니다. 궁극적으로 로그 처리는 Caddy 핵심의 범위를 벗어납니다.

그러나 로그를 소비하는 Caddy 앱 모듈이 존재할 가능성은 항상 열려 있습니다. (우리가 알기로는 아직 존재하지 않을 뿐입니다.)


## 구조화된 로그

대부분의 최신 애플리케이션과 마찬가지로 Caddy의 로그는 *구조화되어* 있습니다. 이는 메시지의 정보가 단순한 불투명 문자열이나 바이트 슬라이스가 아님을 의미합니다. 대신 메시지를 인코딩하여 출력할 때까지 데이터는 강력한 형식을 유지하며 개별 *필드 이름*에 의해 키가 지정됩니다.

기존 HTTP 서버에서 일반적으로 사용되는 오래된 Common Log Format (CLF)과 같은 기존의 비구조화된 로그와 비교해 보세요.

```
127.0.0.1 - - [10/Oct/2000:13:55:36 -0700] "GET /apache_pb.gif HTTP/1.1" 200 2326
```

이 형식은 "구조를 가지고" 있지만 "구조화된" 것은 아닙니다. HTTP 요청을 기록하는 데만 사용할 수 있습니다. 불투명한 바이트 문자열이므로 다르게 인코딩할 (효율적인) 방법이 없습니다. 또한 많은 정보가 누락되어 있습니다. 요청의 Host 헤더조차 포함되어 있지 않습니다! 이 로그 형식은 단일 사이트를 호스팅하고 요청에 대한 가장 기본적인 정보를 얻을 때만 유용합니다.

<aside class="tip">
	CLF에 호스트 정보가 없기 때문에 둘 이상의 사이트를 호스팅할 때 이러한 로그를 별도의 파일에 작성해야 하는 경우가 많습니다. 그렇지 않으면 요청에서 Host 헤더를 알 수 있는 방법이 없습니다!
</aside>

이제 JSON으로 인코딩되고 보기 좋게 포맷된 Caddy의 동등한 구조화된 로그 메시지와 비교해 보세요.

```json
{
	"level": "info",
	"ts": 1646861401.5241024,
	"logger": "http.log.access",
	"msg": "handled request",
	"request": {
		"remote_ip": "127.0.0.1",
		"remote_port": "41342",
		"client_ip": "127.0.0.1",
		"proto": "HTTP/2.0",
		"method": "GET",
		"host": "localhost",
		"uri": "/",
		"headers": {
			"User-Agent": ["curl/7.82.0"],
			"Accept": ["*/*"],
			"Accept-Encoding": ["gzip, deflate, br"],
		},
		"tls": {
			"resumed": false,
			"version": 772,
			"cipher_suite": 4865,
			"proto": "h2",
			"server_name": "example.com"
		}
	},
	"bytes_read": 0,
	"user_id": "",
	"duration": 0.000929675,
	"size": 10900,
	"status": 200,
	"resp_headers": {
		"Server": ["Caddy"],
		"Content-Encoding": ["gzip"],
		"Content-Type": ["text/html; charset=utf-8"],
		"Vary": ["Accept-Encoding"]
	}
}
```

구조화된 로그가 얼마나 더 유용하고 훨씬 더 많은 정보를 포함하는지 확인할 수 있습니다. 이 로그 메시지에 담긴 풍부한 정보는 유용할 뿐만 아니라 사실상 성능 오버헤드 없이 제공됩니다. Caddy의 로그는 제로 할당(zero-allocation)입니다. 구조화된 로그는 데이터 유형이나 컨텍스트에 대한 제한이 없습니다. 어떤 코드 경로에서든 사용할 수 있으며 어떤 종류의 정보라도 포함할 수 있습니다.

로그가 구조화되어 있고 강력한 형식을 갖추고 있으므로 어떤 형식으로든 인코딩할 수 있습니다. 따라서 JSON으로 작업하고 싶지 않다면 로그를 다른 표현으로 인코딩할 수 있습니다. Caddy는 [로그 인코더 모듈](/docs/json/logging/logs/encoder/)을 통해 다른 형식을 지원하며 더 많은 형식을 추가할 수 있습니다.

구조화된 로그와 레거시 형식의 구분에 있어서 **가장 중요한 점**은, 성능 저하를 감수하고라도 구조화된 로그를 [레거시 Common Log Format으로 변환 <img src="/old/resources/images/external-link.svg" class="external-link">](https://github.com/caddyserver/transform-encoder)할 수는 있지만, 그 반대는 불가능하다는 것입니다. CLF에서 구조화된 형식으로 가는 것은 까다롭거나(또는 적어도 비효율적) 정보가 부족하다는 점을 고려할 때 불가능합니다.

본질적으로, 효율적이고 구조화된 로깅은 일반적으로 다음과 같은 철학을 권장합니다:

- 너무 적은 로그보다 너무 많은 로그가 낫다.
- 버리는 것보다 필터링하는 것이 낫다.
- 더 큰 유연성과 상호 운용성을 위해 인코딩을 연기하라.
 

## 생성 (Emission)

코드에서 로그 생성은 다음과 유사합니다:

```go
logger.Debug("proxy roundtrip",
	zap.String("upstream", di.Upstream.String()),
	zap.Object("request", caddyhttp.LoggableHTTPRequest{Request: req}),
	zap.Object("headers", caddyhttp.LoggableHTTPHeader(res.Header)),
	zap.Duration("duration", duration),
	zap.Int("status", res.StatusCode),
)
```

<aside class="tip">
	이것은 Caddy 리버스 프록시의 실제 코드 라인입니다. 디버그 로깅을 활성화했을 때 이 줄을 통해 구성된 업스트림에 대한 요청을 검사할 수 있습니다. 문제 해결 시 이 데이터는 매우 귀중한 자료입니다!
</aside>

이 하나의 함수 호출에 로그 수준, 메시지 및 여러 데이터 필드가 포함되어 있음을 알 수 있습니다. 이 모든 것은 강력한 형식을 갖추고 있으며, Caddy는 제로 할당 로깅 라이브러리를 사용하므로 로그 생성이 빠르고 효율적이며 오버헤드가 거의 없습니다.

`logger` 변수는 이름 및 데이터 필드를 포함하여 모든 양의 컨텍스트를 연결할 수 있는 `zap.Logger`입니다. 이를 통해 로거는 부모 컨텍스트에서 아주 잘 "상속"받을 수 있으므로 고급 추적(tracing) 및 메트릭이 가능해집니다.

거기서부터 메시지는 효율성이 매우 높은 처리 파이프라인을 통해 전송되어 인코딩 및 기록됩니다.


## 로깅 파이프라인

위에서 본 것처럼 메시지는 **로거(loggers)** 에 의해 생성됩니다. 그런 다음 처리를 위해 메시지가 **로그(logs)** 로 전송됩니다.

Caddy를 사용하면 메시지를 처리할 수 있는 [여러 로그를 구성](/docs/json/logging/logs/)할 수 있습니다. 로그는 인코더, 작성기(writer), 최소 수준(level), 샘플링 비율, 그리고 포함하거나 제외할 로거 목록으로 구성됩니다. Caddy에는 항상 `default`라는 이름의 기본 로그가 있습니다. 구성에서 [이 객체](/docs/json/logging/logs/)에 키가 `"default"`로 지정된 로그를 지정하여 사용자 정의할 수 있습니다.

<aside class="tip">

지금이 [Caddy의 로깅 문서](/docs/json/logging/)를 살펴보고 우리가 논의하는 구조와 매개변수에 익숙해질 좋은 시간일 것입니다.

</aside>


- **인코더 (Encoder):** 로그의 형식. 인메모리 데이터 표현을 바이트 슬라이스로 변환합니다. 인코더는 로그 메시지의 모든 필드에 접근할 수 있습니다.
- **작성기 (Writer):** 로그 출력. 파일이나 네트워크 소켓과 같은 모든 로그 기록기 모듈이 될 수 있습니다. 단순히 바이트를 씁니다.
- **수준 (Level):** 로그에는 DEBUG에서 FATAL에 이르는 다양한 수준이 있습니다. 지정된 수준보다 낮은 메시지는 로그에서 무시됩니다.
- **샘플링 (Sampling):** 매우 바쁜(hot) 경로에서는 효과적으로 처리할 수 있는 것보다 더 많은 로그를 생성할 수 있습니다. 샘플링을 활성화하면 메시지의 대표적인 샘플을 생성하면서 부하를 줄일 수 있습니다.
- **포함/제외 (Include/exclude):** 각 메시지는 이름(보통 모듈 ID에서 파생됨)을 가진 로거에 의해 생성됩니다. 로그는 특정 로거의 메시지를 포함하거나 제외할 수 있습니다.

Caddy에서 로그 메시지가 생성될 때:

- 발신 로거의 이름을 각 로그의 포함/제외 목록과 대조하여 확인합니다. 포함된 경우(또는 제외되지 않은 경우) 해당 로그로 허용됩니다.
- 샘플링이 활성화된 경우, 로그 메시지를 유지할지 여부를 결정하기 위한 빠른 계산이 이루어집니다.
- 메시지는 로그에 구성된 인코더를 사용하여 인코딩됩니다.
- 인코딩된 바이트는 로그에 구성된 작성기에 기록됩니다.

기본적으로 모든 메시지는 구성된 모든 로그로 이동합니다. 이는 위에서 설명한 구조화된 로깅의 가치를 고수하는 것입니다. 포함/제외 목록을 설정하여 어떤 메시지가 어떤 로그로 갈지 제한할 수 있지만, 이것은 주로 서로 다른 모듈의 메시지를 필터링하기 위한 것이며 로그 집계 서비스처럼 사용하려는 의도는 아닙니다. Caddy의 로깅 파이프라인을 간소화하고 효율적으로 유지하기 위해 로그 메시지의 고급 처리는 소비(consumption) 단계로 미뤄집니다.

## 소비 (Consumption)

메시지가 출력으로 전송된 후 소비자가 메시지를 읽고, 파싱하며 그에 따라 처리합니다.

이것은 로그 생성과는 매우 다른 문제 영역이며 Caddy의 핵심은 소비를 처리하지 않습니다(Caddy 앱 모듈이 처리할 수는 있지만). JSON 메시지 스트림(또는 다른 형식)을 처리하고 로그를 확인, 필터링, 색인화 및 조회하는 데 사용할 수 있는 수많은 도구가 있습니다. 직접 작성하거나 구현할 수도 있습니다.

예를 들어, 특정 필드(예: 호스트 이름)에 따라 여러 파일로 분리된 CLF를 요구하는 레거시 소프트웨어를 실행하는 경우, JSON을 읽고 `sprintf()`를 호출하여 CLF 문자열을 만든 다음 `request.host` 필드의 값에 따라 파일에 기록하는 간단한 도구를 사용하거나 작성할 수 있습니다.

Caddy의 로깅 기능을 사용하여 메트릭과 추적을 구현할 수도 있습니다. 메트릭은 기본적으로 특정 특성을 가진 메시지 수를 세고, 추적은 공통점을 기반으로 여러 메시지를 서로 연결합니다.

Caddy의 로그를 소비하여 할 수 있는 일은 무궁무진합니다!
