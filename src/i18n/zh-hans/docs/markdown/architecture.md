架构
============

Caddy 是一个单一、独立的静态二进制文件，没有任何外部依赖，因为它是用 Go 编写的。这些特性构成了项目愿景的重要部分，因为它们简化了部署，并减少了生产环境中繁琐的排障工作。

如果没有动态链接，那它又是如何扩展的？Caddy 采用了一种新颖的插件架构，使其能力远远超出其他任何 Web 服务器，甚至包括那些带有外部（动态链接）依赖的服务器。

我们“减少活动部件”的理念，最终带来的是更可靠、更易管理、成本更低的网站，尤其是在大规模场景下。这篇偏技术性的文档说明了我们如何通过软件工程实现这个目标。


## 概览

Caddy 由命令、核心库和模块组成。

**命令**提供了你应该已经熟悉的[命令行界面](/docs/command-line)。它就是你从操作系统启动进程的方式。这部分代码和逻辑都很少，只包含按用户期望方式启动核心所需的内容。除了与启动配置有关的部分，我们刻意避免使用标志和环境变量来做配置。


<aside class="tip">

模块可以向命令行界面添加子命令！比如，[`caddy file-server`](/docs/command-line#caddy-file-server) 命令就是这样来的。尽管 Caddy 核心命令尽量少用标志和环境变量，这些新增命令仍然可以按需使用任意标志或环境变量。

</aside>


**[核心库](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc)**，也就是 Caddy 的“core”，主要负责配置管理。它可以[`Run()`](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Run)一个新配置，也可以[`Stop()`](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Stop)一个正在运行的配置。它还为模块提供各种工具、类型和值。

**模块**负责其余所有事情。Caddy 内置了许多模块，这些称为*标准模块*。这些模块被认为是对大多数用户最有用的。


<aside class="tip">

有时，“模块”、“插件”和“扩展”这几个词会互换使用，通常这样也没问题。从技术上说，所有模块都是插件，但并非所有插件都是模块。模块特指一种会扩展 Caddy [配置结构](/docs/json/)的插件。

</aside>




## Caddy core

从本质上说，Caddy 只是加载一个初始配置（config）；如果没有初始配置，就打开一个套接字，稍后再接受新的配置。

[Caddy 配置](/docs/json/)是一个 JSON 文档，顶层有一些字段：

```json
{
	"admin": {},
	"logging": {},
	"apps": {•••},
	...
}
```

Caddy 核心可以原生处理其中一些字段：

- [`admin`](/docs/json/admin/) 用于搭建[管理 API](/docs/api)并管理进程
- [`logging`](/docs/json/logging/) 用于[输出日志](/docs/logging)

但其他顶层字段，比如 [`apps`](/docs/json/apps/)，对 Caddy 核心来说是透明的。事实上，Caddy 对 `apps` 里的字节唯一知道的事，就是把它们反序列化成一个接口类型，然后调用它的两个方法：

1. `Start()`
2. `Stop()`

就这样。加载配置时，它对每个 app 调用 `Start()`；卸载配置时，对每个 app 调用 `Stop()`。

当一个 app 模块启动后，它就会启动该 app 的模块生命周期。


<aside class="tip">

如果你是正在编写 Caddy 模块的程序员，可以在我们的[扩展 Caddy](/docs/extending-caddy)指南中找到类似信息，不过那里的重点更偏向代码。

</aside>


## 模块生命周期

模块分为两类：*宿主模块*和*客体模块*。

**宿主模块**（或“父”模块）是加载其他模块的模块。

**客体模块**（或“子”模块）是被加载的模块。所有模块都是客体模块，即使是 app 模块也一样。

模块会按以下顺序经历加载、配置和验证、使用、清理这几个阶段：

1. 加载
2. 配置并验证
3. 使用
4. 清理

当配置被加载时，Caddy 会先初始化所有已配置的 app 模块，从而启动模块生命周期。之后，每个 app 模块都会继续把这个过程向下传递。

### 加载阶段

加载模块，就是把它的 JSON 字节反序列化成内存中的一个类型化值。基本上就是这样，只是把 JSON 解码成一个值。

### 配置阶段

这个阶段负责大部分初始化工作。所有模块在加载之后都会有机会自行配置。

由于 JSON 编码中的属性已经被解码完毕，这里只需要进行额外的设置。配置阶段最常见的任务是初始化客体模块。换句话说，配置宿主模块时，也会一路向下配置它的客体模块。

你可以通过[浏览文档中的 Caddy JSON 结构](/docs/json/)来理解这一点。凡是看到 `{•••}` 的地方，都可能会用到客体模块；点进去之后，你可以继续一路往下看，直到不再有客体模块为止。

其他常见的配置任务包括设置模块生命周期内会用到的内部值，或者规范化输入。例如，[`http.matchers.remote_ip`](/docs/modules/http.matchers.remote_ip) 模块会在配置阶段，把它从 JSON 字符串输入里收到的 CIDR 值解析出来。这样它就不必在每个 HTTP 请求里都做这件事，因此效率更高。

验证也可以在配置阶段进行。如果模块生成的配置无效，就可以在这里返回错误，从而中止整个配置加载过程。

### 使用阶段

一旦客体模块完成配置并通过验证，它就可以被宿主模块使用。具体意味着什么，取决于每个宿主模块。

每个模块都有一个 ID，它由一个命名空间以及该命名空间中的名字组成。例如，[`http.handlers.reverse_proxy`](/docs/modules/http.handlers.reverse_proxy) 是一个 HTTP handler，因为它位于 `http.handlers` 命名空间中，名字是 `reverse_proxy`。`http.handlers` 命名空间中的所有模块都满足同一个接口，而这个接口是宿主模块所知道的。因此，`http` app 知道如何加载并使用这类模块。

### 清理阶段

当配置需要停止时，所有模块都会被卸载。如果某个模块分配了需要释放的资源，它就可以在清理阶段释放它们。


## 插件接入

通过为模块包添加 `import`，一个模块，或者任意 Caddy 插件，就“接入”到了 Caddy 中。导入该包后，[模块会自行注册](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#RegisterModule)到 Caddy 核心，因此 Caddy 进程启动时就能按名称识别每个模块。它甚至可以在模块值和名称之间建立双向关联。


<aside class="tip">

无需修改 Caddy 代码库，就可以添加插件。具体做法在 [readme](https://github.com/caddyserver/caddy/#with-version-information-andor-plugins) 中有说明。

</aside>


## 配置管理

要修改正在运行的服务器的当前配置（通常称为“reload”），并不容易，因为服务器往往要处理高并发和大量参数。Caddy 用一种设计优雅地解决了这个问题，这种设计带来了很多好处：

- 不会中断正在运行的服务
- 可以进行细粒度的配置变更
- 只需要一个锁（在后台）
- 所有 reload 都是原子、一致、隔离且大体持久的（“ACID”）
- 全局状态极少

你可以[观看一段介绍 Caddy 2 设计的视频](https://www.youtube.com/watch?v=EhJO8giOqQs)。

配置 reload 的工作方式是先配置新模块；如果全部成功，旧模块就会被清理。在一小段时间里，两个配置会同时处于可用状态。

每个配置都关联着一个[context](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Context)，其中保存着所有模块状态，所以大部分状态都不会逃出配置的作用域。这对正确性、性能和简洁性都有好处。

不过，有时确实需要真正的全局状态。例如，反向代理可能会跟踪其上游的健康状况；由于每个上游在全局范围内只有一个实例，如果每次做小的配置变更都把它们忘掉，那就很糟糕了。幸运的是，Caddy [提供了相关机制](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#UsagePool)，类似于语言运行时的垃圾回收器，用来保持全局状态整洁。

对于在线配置更新，一个显而易见的做法，是给每个配置参数都加同步，即使是在热点路径上也这么做。这在性能和复杂度上都糟糕得离谱，尤其在大规模场景下，因此 Caddy 不采用这种方式。

相反，配置会被视为不可变的原子单元：要么整个替换，要么什么都不改。[管理 API 端点](/docs/api) 允许通过遍历结构进行细粒度修改，但它们只会修改配置的内存表示，再由此生成并加载一份全新的配置文档。这种方法在简洁性、性能和一致性方面都有很大优势。由于只有一个锁，Caddy 也能轻松处理快速 reload。
