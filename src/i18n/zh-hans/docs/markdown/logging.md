日志记录的工作原理
=================

Caddy 拥有功能强大且灵活的日志记录功能，但这些功能可能与您习惯的不同，特别是如果您之前使用的是较为陈旧的共享主机或其他老旧的 Web 服务器。


## 概述

日志记录主要有两个方面：生成和处理。

**发送**是指生成消息。它包括三个步骤：

1. 收集相关信息（背景）
2. 构建有用的表示（编码）
3. 将该表示形式发送到输出（写入）

此功能已深度集成到 Caddy 的核心中，使得 Caddy 代码库或模块（插件）的任何部分都能输出日志。

**处理**是指对日志消息的接收和处理。为了发挥作用，生成的日志必须被下游处理。那些仅被写入却从未被读取的日志毫无价值。日志处理可以简单到管理员阅读控制台输出，也可以复杂到接入日志聚合工具或云服务，以对日志消息进行过滤、计数和索引。

### Caddy 的角色

*Caddy 是一个日志输出器*。它不会消耗日志，仅进行编码和写入日志所需的最低限度的处理。这一点很重要，因为它使 Caddy 的核心更加简洁，从而减少了错误和边界情况，同时降低了维护负担。归根结底，日志处理不在 Caddy 核心的范围之内。

不过，未来可能会出现一个用于处理日志的 Caddy 应用模块。（据我们所知，目前还尚未存在。）


## 结构化日志

与大多数现代应用程序一样，Caddy 的日志是*结构化的*。这意味着消息中的信息不仅仅是一个不透明的字符串或字节片段。相反，数据始终保持强类型，并以各个*字段名称*作为键，直到需要对消息进行编码并写入时为止。

与传统 HTTP 服务器中常用的传统非结构化日志（如过时的通用日志格式（CLF））相比：

```
127.0.0.1 - - [10/Oct/2000:13:55:36 -0700] "GET /apache_pb.gif HTTP/1.1" 200 2326
```

这种格式“具有结构”，但并非“结构化”的：它只能用于记录 HTTP 请求。由于它是一串不透明的字节，因此无法（高效地）以其他方式对其进行编码。此外，它还缺少大量信息，甚至不包含请求的 Host 头部！这种日志格式仅在托管单个网站时有用，且仅能获取关于请求的最基本信息。

<aside class="tip">
	CLF 中缺少主机信息，这就是为什么在托管多个网站时，通常需要将这些日志写入单独的文件：否则就无法从请求中获取 Host 头部信息！
</aside>

现在，让我们对比一下 Caddy 生成的等效结构化日志消息，该消息采用 JSON 格式编码，并经过精心排版以便显示：

```json
{
	"level": "info",
	"ts": 1646861401.5241024,
	"logger": "http.log.access",
	"msg": "handled request",
	"request": {
		"remote_ip": "127.0.0.1",
		"remote_port": "41342",
		"client_ip": "127.0.0.1",
		"proto": "HTTP/2.0",
		"method": "GET",
		"host": "localhost",
		"uri": "/",
		"headers": {
			"User-Agent": ["curl/7.82.0"],
			"Accept": ["*/*"],
			"Accept-Encoding": ["gzip, deflate, br"],
		},
		"tls": {
			"resumed": false,
			"version": 772,
			"cipher_suite": 4865,
			"proto": "h2",
			"server_name": "example.com"
		}
	},
	"bytes_read": 0,
	"user_id": "",
	"duration": 0.000929675,
	"size": 10900,
	"status": 200,
	"resp_headers": {
		"Server": ["Caddy"],
		"Content-Encoding": ["gzip"],
		"Content-Type": ["text/html; charset=utf-8"],
		"Vary": ["Accept-Encoding"]
	}
}
```

您可以看出，结构化日志不仅实用得多，而且包含的信息也更为丰富。该日志消息中丰富的信息不仅实用，而且几乎不会带来任何性能开销：Caddy 的日志不占用内存空间。结构化日志对数据类型或上下文没有限制：它们可以在任何代码路径中使用，并包含任何类型的信息。

由于日志具有结构化且强类型化的特点，因此可以编码为任何格式。因此，如果您不想使用 JSON，可以将日志编码为任何其他表示形式。Caddy 通过[日志编码器模块](/docs/json/logging/logs/encoder/)支持其他格式，并且还可以添加更多格式。

**最重要的是**，在结构化日志与传统格式的区别中，尽管会带来性能开销，但结构化日志<a href="https://github.com/caddyserver/transform-encoder">可以转换为传统的通用日志格式 <img src="/old/resources/images/external-link.svg" class="external-link"></a>，反之则不可行。将通用日志格式转换为结构化格式并非易事（或至少效率低下），而且鉴于信息缺失，这种转换更是不可能实现的。

本质上，高效且结构化的日志记录通常体现了以下理念：

- 日志多总比少好
- 筛选优于丢弃
- 延迟编码以提高灵活性和互操作性
 

## 排放

在代码中，日志输出通常如下所示：

```go
logger.Debug("proxy roundtrip",
	zap.String("upstream", di.Upstream.String()),
	zap.Object("request", caddyhttp.LoggableHTTPRequest{Request: req}),
	zap.Object("headers", caddyhttp.LoggableHTTPHeader(res.Header)),
	zap.Duration("duration", duration),
	zap.Int("status", res.StatusCode),
)
```

<aside class="tip">
	这是 Caddy 反向代理中的一行实际代码。当启用调试日志记录时，正是这一行代码允许您检查发往已配置上游服务器的请求。在排查故障时，这是一条极其宝贵的信息！
</aside>

你可以看到，这个函数调用包含日志级别、一条消息以及若干数据字段。所有这些都是强类型的，而且 Caddy 使用了一个零分配日志库，因此日志输出既快速又高效，几乎没有开销。

该 `logger` 变量是一个 `zap.Logger` ，可能与其关联任意数量的上下文，这些上下文包含名称和数据字段。这使得日志记录器能够非常顺畅地“继承”父上下文，从而支持高级追踪和指标功能。

随后，该消息将通过一条高效的处理管道进行传输，在此过程中完成编码并写入。


## 日志管道

如上所述，消息由**日志器**发出。随后，这些消息会被发送到**日志**中进行处理。

Caddy 允许您[配置多个日志](/docs/json/logging/logs/)，用于处理消息。一个日志由编码器、写入器、最低级别、采样率以及包含或排除的日志器列表组成。在 Caddy 中，始终存在一个名为 `default`。您可以通过在配置中指定以 `"default"` 作为[键](/docs/json/logging/logs/)的日志[键](/docs/json/logging/logs/)。

<aside class="tip">

现在正是[查阅 Caddy 日志文档](/docs/json/logging/)的好时机，这样您就能熟悉我们所讨论的结构和参数。

</aside>


- **编码器：** 日志的格式。将内存中的数据表示转换为字节数组。编码器可以访问日志消息的所有字段。
- **写入器：** 日志输出。可以是任何日志写入模块，例如写入文件或网络套接字。它仅负责写入字节。
- **级别：** 日志有不同的级别，从 DEBUG 到 FATAL。低于指定级别的消息将被日志忽略。
- **采样：** 极度繁忙的路径生成的日志可能超出有效处理能力；启用采样可在减轻负载的同时，仍能获取具有代表性的消息样本。
- **包含/排除：** 每条消息都由一个日志记录器发出，该日志记录器有一个名称（通常由模块 ID 衍生而来）。日志可以包含或排除来自特定日志记录器的消息。

当 Caddy 输出日志消息时：

- 会将原始日志记录者的名称与每个日志的包含/排除列表进行比对；如果被包含（或未被排除），则允许其进入该日志。
- 如果启用了采样功能，系统会通过快速计算来决定是否保留日志消息。
- 该消息使用日志中配置的编码器进行编码。
- 随后，这些编码后的字节会被写入日志的配置写入器。

默认情况下，所有消息都会写入所有已配置的日志文件。这符合上文所述的结构化日志记录原则。您可以通过设置包含/排除列表来限制哪些消息写入哪些日志文件，但这主要用于过滤来自不同模块的消息；其设计初衷并非作为日志聚合服务使用。为了保持 Caddy 日志管道的简洁和高效，日志消息的高级处理被推迟到处理阶段进行。

## 处理

消息发送到输出端后，下游处理器会将其读取、解析，并进行相应处理。

这与日志输出属于截然不同的问题领域，Caddy 的核心并不负责日志处理（尽管 Caddy 应用模块当然可以做到这一点）。市面上有许多工具可用于处理 JSON 消息流（或其他格式），并实现日志的查看、过滤、索引和查询。你甚至可以编写或实现自己的工具。

例如，如果您运行的旧版软件需要根据特定字段（例如主机名）将 CLF 拆分为不同的文件，您可以使用或编写一个简单的工具，该工具读取 JSON 数据，调用 `sprintf()` 来生成 CLF 字符串，最后根据 `request.host` 字段的值将其写入文件。

Caddy 的日志记录功能也可用于实现指标和追踪：指标主要是统计具有特定特征的消息，而追踪则是根据消息之间的共同点将多条消息关联起来。

利用 Caddy 的日志，您可以做的事情不胜枚举！
